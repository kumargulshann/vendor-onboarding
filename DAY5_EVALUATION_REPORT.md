# Day 5 — Decision Reliability Evaluation

**Goal:** measure how reliably the vendor-onboarding workflow makes and explains
decisions on **unfamiliar** vendor submissions. All runs use synthetic data and
isolated run storage; no live vendor data is touched.

**Build:** PS-2 vendor onboarding. The initial run and each retest are reported below.

---

## 1. The three Day-4 findings — closed and verified

| # | Finding | Fix | Verified |
|---|---------|-----|----------|

| 3 | **Only the latest pending attempt can be corrected; the server must check the expected predecessor before appending.** | `_resolve_case()` takes `expected_previous_run_id`, sets `predecessor_stale` + `correction_allowed`; `_refresh_correction_allowed()` recomputes (latest attempt, pending only). **One consequential failure found and fixed during Day 5.** The deterministic
fallback *reasoning* text restated each failed check's full detail — which is the
**same text** as the vendor-facing action — so the account-mismatch message was
shown twice (once in Reasoning, once in the vendor response). Fixed in
`app/ai_layer.py`: reasoning now lists the failed check **names** and points to
the vendor response, so each action is shown exactly once. A regression test
locks this in. This was the fix that closed finding #2 in the browser.

## 3. Repeatable command

```bash
# one-time: start the app
cd vendor_onboarding && bash run.sh            # http://localhost:8000

# regenerate fixtures + recorded expectations (optional; inputs are fixed)
python3 -m tests.make_eval_fixtures

# run the evaluation through the normal application entry point (/api/run)
python3 -m tests.run_eval

# regression suite
python3 -m pytest -q

# browser verification of the three Day-4 fixes
python3 tests/ui_check_day5.py
```

`tests/run_eval.py` posts each case through `POST /api/run` — JSON, or
**multipart with an actual PDF** for the PDF cases — then compares the decision
**and** the explanation against the recorded expectations, writing
`data/eval/results.json` and printing the counts and denominators.

**Regression suite:** `python3 -m pytest -q` → **70 passed** (56 Day-2/3/4 + 6
Day-5 implementation + 4 Day-5 behavior-lock + 4 Day-6 stale-correction tests).

**Browser verification:** all three Day-4 fixes confirmed
(`tests/ui_check_day5.py` → **ALL DAY-5 UI CHECKS PASSED**), including that each

### Limits of the sample
- 16 synthetic cases, all fictional, generated from the same policy engine.
- Decisions are deterministic (rule-based); no live LLM is exercised by default,
  so this measures the **rule pipeline's** reliability, not stochastic model
  behaviour.
- The sample is deliberately adversarial on formatting/evidence variety but is
  still small; it confirms correctness on the covered scenarios, not statistical
  coverage of the whole vendor population.

## 5. Finding for a procurement buyer

**When a vendor corrects a submission, the system now tells you exactly where
the submission stands and what the vendor must still do — in one place, without
repeating itself.**

Before this change, if a vendor fixed one problem but introduced another (for
example, uploaded the missing documents but typed a bank account that does not
match the bank letter), the reviewer saw the same "account mismatch" instruction
twice — once in the reasoning and once in the vendor message — and had to
reconstruct the current status by hand. Now the decision panel leads with the
**current decision and the full list of remaining blockers**, shows **both
attempt timestamps** so you can see what changed, and shows each required vendor
action **exactly once**.

Practically, that means a reviewer handling a correction spends less time
decoding conflicting messages and can act on the single, current list of what
the vendor still owes. In the 16-case evaluation, **0 of 5** approval-worthy
submissions were held or rejected unnecessarily, and **0 of 11** held/rejected
cases were approved with a real defect — the decisions and their explanations
matched the policy expectations on every case.

The evaluation also confirmed the guardrail that matters most to a buyer: a
vendor **cannot** correct an older attempt after a newer one has been saved.
The server verifies the declared predecessor and appends only if it is still
the case's latest pending attempt — the check and the append are one atomic
operation. A stale correction is **rejected with zero attempts created**, and
the reviewer is shown a readable conflict message with a direct link to the
latest attempt. This was verified in the browser by opening the same pending
attempt in two tabs: saving a correction in tab A, then submitting the old
form in tab B left the case at exactly **two attempts** with the latest
decision unchanged, and tab B was directed to attempt 2 (both when tab A's
correction stayed pending and when it approved). This protects the audit trail
from silent, out-of-order edits.

## 6. Day 6 — stale corrections fixed at the point of saving

**Finding that drove this.** A correction opened against an old attempt could
still be submitted after a newer attempt had been saved: the server appended it
as a new attempt flagged `predecessor_stale: true` instead of refusing it. That
contradicted the claim that the server prevents stale corrections.

**Fix.** A correction now identifies its case **and** its expected previous run,
and the server appends it only if that run is still the case's latest attempt
**and** is pending. The predecessor check and the append are a **single atomic
operation** under the run lock, so no other save can slip in between. A stale
correction, a correction to a closed case, or an unknown/mismatched target
raises `CorrectionConflict` and creates **zero attempts**. The new-case path
(no `case_id`, no predecessor) is unchanged and always starts a fresh case.

**Conflict feedback.** Both submission paths (JSON `POST /api/run` and the
streaming form/PDF path `POST /api/run/stream`) return a readable conflict
message plus the latest attempt id/number. The UI shows the message and an
**"Open latest attempt"** button that loads that attempt directly.

**Changed files:**
- `app/runner.py` — `CorrectionConflict` exception; `_intend_case()` decides
  new-vs-correction; `_finalize_and_append()` does the atomic verify-and-append;
  `run_process()` uses them (removed the old `_resolve_case` stale-append logic).
- `app/main.py` — `api_run` returns HTTP 409 with a structured conflict body;
  the streaming worker emits a conflict error event with the latest-attempt info.
- `templates/index.html` — `showConflict()` renders the message + "Open latest
  attempt" button; the streaming error handler detects a `conflict` payload.
- `tests/test_regression.py` — the old test that expected a stale append to
  succeed was replaced with tests for the intended behavior (stale → zero
  attempts; closed case → zero attempts; unknown target → zero attempts; valid
  correction appends with a verified predecessor; new-case path works). Existing
  correction tests updated to declare their predecessor.

**Two-tab browser acceptance (`tests/ui_check_day6.py`):**
- Scenario 1 (tab A's correction stays pending): case stayed at **2 attempts**,
  latest `pending`; tab B showed the conflict and opened attempt 2.
- Scenario 2 (tab A's correction approves): case stayed at **2 attempts**,
  latest `approved`; tab B showed the conflict and opened attempt 2.
- No bank-sensitive data leaked in any response.

**Re-run after the fix:** full regression suite **70 passed**; all 16 evaluation
cases still **16/16** (status, blocking reasons, vendor actions), 0/11 incorrect
approvals, 0/5 unnecessary holds.

## 7. Final local retest

The save path requires both identifiers for a correction and checks that the
predecessor belongs to the supplied case. A fresh submission supplies neither
identifier. The server writes a completed attempt and its comparison to disk
before publishing it in history. A simulated write failure left the previous
attempt current and allowed a retry.

The local suite passed **71 tests**. The 16-case API retest reproduced the
saved retest row for row. In Chrome, both stale-tab scenarios kept exactly
two attempts. An app restart recovered the corrected case and its comparison
from isolated demo storage.
